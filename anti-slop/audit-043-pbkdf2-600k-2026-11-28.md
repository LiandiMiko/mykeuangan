# Audit 043: Gelombang 7b — PBKDF2 100rb → 600rb Iterasi, Migrasi Transparan — 2026-11-28

Status: Complete (1 branch `fix/gelombang-7b-pbkdf2` dari `origin/main 41161f9`, v3.20.12 → **v3.20.15** / `versionCode 3020015`; PR BELUM dibuat saat dokumen ini ditulis — belum di-merge; pengujian manual di perangkat fisik belum dilakukan; tidak ada perubahan database, Edge Function, atau produksi Supabase — ini murni client-side)

## Cakupan

Gelombang 7b item 2: dua situs PBKDF2-100rb di klien harus naik ke 600rb iterasi, mengikuti rekomendasi OWASP Password Storage Cheat Sheet (PBKDF2-HMAC-SHA256: 600.000 iterasi — diverifikasi dari https://cheatsheetseries.owasp.org/cheatsheets/Password_Storage_Cheat_Sheet.html pada 2026-11-28: "If FIPS-140 compliance is required, use PBKDF2 with a work factor of 600,000 or more and set with an internal hash function of HMAC-SHA-256"). Backup JSON sudah 600rb sejak lama (`web/ui-feat-backup.js:64` `BACKUP_PBKDF2_ITERATIONS = 600000`, fallback legacy 150rb) dan tidak disentuh. Yang diubah: (a) hash verifikasi PIN di `web/ui-feat-account.js` (`derivePinHash`, ~baris 318), dan (b) KEK pembungkus DEK di `web/ui-feat-offline.js` (`pinCrypto.derivePinKek`, ~baris 172-199). Keduanya harus bermigrasi transparan: pengguna lama tidak boleh diminta ganti PIN, tidak boleh kehilangan data lokal, dan PIN salah tidak boleh memicu migrasi apa pun. Lockout/backoff PIN, biometrik, dan penanganan wrap rusak harus dipertahankan apa adanya.

## Temuan Forensik

- **Dua situs 100rb, satu format tanpa iterasi tersimpan**: hash verifikasi PIN memakai `deriveBits` PBKDF2 100.000 dan menyimpan hasilnya sebagai `pbkdf2$<hex>` — jumlah iterasi TIDAK tersimpan di format ini, jadi kode lama tidak bisa membedakan hash 100rb dari hash beriterasi lain. Sebaliknya, wrap DEK SUDAH menyimpan `iterations: 100000` di JSON (`{kdf:'PBKDF2-SHA256', iterations, salt, iv, wrappedKey}`) — tetapi `unwrapPinDataKey` lama MENGABAIKAN field itu dan selalu menderivasi KEK dengan 100.000 hardcode. Artinya: menaikkan angka di `wrapPinDataKey` saja tanpa menyentuh `unwrapPinDataKey` akan MENGUNCI semua pengguna lama keluar (wrap baru 600rb tidak bisa dibuka oleh unwrap 100rb), dan menaikkan angka di `derivePinHash` saja akan membuat SEMUA hash lama gagal verifikasi. Kedua sisi baca harus diperbaiki bersamaan — ini temuan kunci audit ini.
- **Preseden migrasi transparan sudah ada di fungsi yang sama**: `verifyPinMatches` sudah memigrasi hash legacy SHA-256 (tanpa salt) ke PBKDF2 bila PIN benar sebelum cut-off v3.20.7, dan menolak legacy setelah cut-off. Pola "verifikasi dulu dengan parameter lama, lalu re-hash dengan parameter baru dan simpan" dipakai ulang untuk migrasi 100rb → 600rb — tidak ada mekanisme migrasi baru yang ditemukan.
- **Alur ganti PIN sudah memusatkan pembuatan hash + wrap**: `applyAccountSettingsUpdate` memanggil `rewrapPinDataKey(oldPin, newPin)` (→ `wrapPinDataKey`) lalu `hashPin(val.pin)`; `saveInitialAppPin` (onboarding) memanggil `hashPin` + `createPinDataKey` (→ `wrapPinDataKey`). Karena itu kedua jalur otomatis 600rb begitu konstanta di dua fungsi kanonis itu naik — tidak ada situs pembuatan hash/wrap lain (sapuan `grep -rn "derivePinKek\|derivePinHash\|pbkdf2\$" web/ src/` di luar kedua file ini kosong).
- **Kenapa tetap PBKDF2, bukan Argon2id**: OWASP menempatkan Argon2id sebagai pilihan pertama, PBKDF2 sebagai pilihan bila FIPS-140 disyaratkan. Di Web Crypto browser tidak tersedia Argon2id/scrypt — PBKDF2 adalah satu-satunya KDF yang tersedia di `crypto.subtle` — jadi menaikkan iterasi PBKDF2 ke angka rekomendasi OWASP adalah perbaikan yang benar di platform ini, bukan ganti algoritma.
- **Biaya performa nyata, bukan klaim**: di VM pengujian (Node v24.22.1, 4 CPU), satu PBKDF2-600k memakan median ~680 ms vs ~122 ms pada 100k (diukur 5 run per konfigurasi, lihat Verifikasi). Jalur unlock menghitung PBKDF2 DUA kali berurutan — verifikasi hash (`deriveBits`) + unwrap KEK (`deriveKey`) — jadi ≈ 1,4 detik di VM ini; ganti PIN tiga kali (≈ 2,0 detik: verifikasi + rewrap + hash baru). Di WebView Android kelas bawah, perkiraan tugas (1–3 detik saat unlock) masuk akal dan TIDAK dibantah oleh angka ini — justru angka ini yang menjadi dasarnya. 600rb dipertahankan karena itu angka OWASP; bila pengukuran perangkat fisik membuktikan tidak layak, keputusan menurunkan angka adalah keputusan Liandi/koordinator, bukan pekerja (tidak ada penurunan diam-diam di branch ini).
- **Label statis "Menampilkan 33 rilis" sudah basi sebelum bump — seperti pola audit-038**: `grep -c 'data-release-card' src/updates.html` = 34 setelah kartu baru (33 sebelumnya); label diperbarui ke 34. Asersi dinamis di `tests/pro-web-ui.test.js:229-230` menghitung dari jumlah kartu, jadi tetap lolos tanpa perubahan.

## Perubahan yang Diterapkan

1. **KEK/DEK — `web/ui-feat-offline.js` (+27/−6)**: konstanta baru `PIN_KEK_PBKDF2_ITERATIONS = 600000` + `PIN_KEK_PBKDF2_LEGACY_ITERATIONS = 100000`. `derivePinKek(pin, saltBytes, iterations)` kini menerima parameter iterasi opsional (default 600rb, dibulatkan ke bawah, fallback 600rb bila tidak valid). `wrapPinDataKey` menulis `iterations: 600000`. `unwrapPinDataKey` kini MENGHORMATI `wrap.iterations` yang tersimpan (`Number(w.iterations) > 0 ? … : 100000`) — wrap lama 100rb dan wrap tanpa field `iterations` sama sekali dibuka dengan 100rb. `pinCrypto` mengekspor `KEK_ITERATIONS` / `KEK_LEGACY_ITERATIONS` (satu sumber angka target untuk migrasi wrap di `ui-feat-account.js`). Komentar header envelope diperbarui (100.000 → 600.000 + catatan migrasi).
2. **Hash verifikasi PIN — `web/ui-feat-account.js` (+99/−7)**: konstanta baru `PIN_PBKDF2_ITERATIONS = 600000` + `PIN_PBKDF2_LEGACY_ITERATIONS = 100000`. `derivePinHash(pin, saltHex, iterations)` kini mengembalikan format baru yang membawa iterasi — `pbkdf2$600000$<hex>` — dengan hex dihitung `derivePinHashHex(pin, saltHex, iterations)` (fungsi baru, diekspor untuk tes). Helper baru `parsePinHashIterations(savedHash)` (format baru → angkanya; `pbkdf2$<hex>` lama → 100000; bukan format pbkdf2 → null) dan `extractPinHashHex(savedHash)` (ambil hex tanpa peduli format). `verifyPinMatches`: untuk hash `pbkdf2$`, derivasi memakai iterasi yang TERSIMPAN, bandingkan hex saja (bukan string utuh, karena format lama vs baru berbeda); bila PIN benar DAN iterasi tersimpan < 600000 → migrasi transparan via `hashPin(pin)` (salt baru, format baru) — dibungkus try/catch supaya kegagalan penyimpanan tidak pernah mengubah PIN benar menjadi gagal verifikasi; hash lama tetap valid dan migrasi dicoba lagi saat unlock berikutnya. PIN salah return false sebelum baris migrasi mana pun — tidak ada yang dimigrasi. Jalur legacy SHA-256 (S6) tidak berubah, hanya saja hasil migrasinya kini otomatis format 600rb karena lewat `hashPin`.
3. **Migrasi wrap — `web/ui-feat-account.js` (fungsi baru `migratePinDataKeyWrapIterations`)**: dipanggil sebagai hook di `ensurePinDataKeyAfterUnlock` SETELAH `unwrapPinDataKey(pin)` berhasil. Membaca wrap tersimpan; bila `iterations < target` (target dibaca dari `pinCrypto.KEK_ITERATIONS`, fallback 600000), membungkus ulang DEK YANG SAMA lewat `wrapPinDataKey` (salt + IV baru, 600rb), lalu MENYIMPAN wrap baru — wrap lama tidak pernah dihapus/di-overwrite sebelum penggantinya aman tersimpan (wrap baru dihitung penuh dulu). Fail-soft: bila re-wrap gagal, return false dan aplikasi tetap jalan dengan wrap lama; migrasi dicoba lagi saat unlock berikutnya. Tidak pernah membuat DEK baru, tidak pernah mengunci pengguna keluar. Bila wrap sudah 600rb → return false (tidak ada kerja).
4. **Ekspor test/diagnostic — `web/ui-feat-account.js`**: `root.__mkFeat.pinDataKey = { createPinDataKey, unwrapPinDataKey, rewrapPinDataKey, ensurePinDataKeyAfterUnlock, migratePinDataKeyWrapIterations }` (preseden: `wave3Auth` sudah mengekspos internal untuk tes) dan `wave3Auth` kini juga mengekspor `derivePinHashHex`, `parsePinHashIterations`, `PIN_PBKDF2_ITERATIONS`, `PIN_PBKDF2_LEGACY_ITERATIONS`. Komentar jalur ganti PIN di `applyAccountSettingsUpdate` mencatat bahwa rewrap + `hashPin` kini 600rb; komentar blok K2 diperbarui (600.000 + catatan migrasi).

## Catatan Migrasi Pengguna

- **Bagi pengguna setelah update ke v3.20.15**: tidak ada yang perlu dilakukan. Saat PIN benar pertama kali dimasukkan setelah update, hash verifikasi PIN dan bungkus kunci data lokal diam-diam naik ke 600.000 iterasi. PIN tetap sama, data lokal tetap bisa dibuka, tidak ada layar atau langkah tambahan.
- **Bagi pengguna yang PIN-nya salah**: tidak ada perubahan apa pun — PIN salah tetap ditolak dan pengaman lama tetap apa adanya sampai PIN benar dimasukkan.
- **Bagi pengguna yang membuka kunci dengan sidik jari**: biometrik tetap membutuhkan PIN sekali per buka aplikasi (keterbatasan Wave 1, tidak diubah); migrasi terjadi pada entri PIN itu.
- **Yang akan terasa**: buka kunci bisa sedikit lebih lama — di komputer pengujian satu hitungan 600rb ≈ 0,7 detik dan unlock menghitung dua kali (≈ 1,4 detik); di HP kelas bawah diperkirakan 1–3 detik. Ini harga keamanan 6x lebih kuat, hanya saat buka kunci (bukan saat memakai aplikasi).
- **Jalur darurat bila wrap rusak**: tidak berubah — bila wrap kunci data rusak padahal PIN benar, aplikasi membuat kunci baru agar tetap bisa jalan; data lokal lama yang terenkripsi dengan kunci lama menjadi tidak bisa dibaca (bukan crash).
- Update ke v3.20.15 menimpa v3.20.12 tanpa uninstall (`versionCode 3020015` > `3020012` — monoton). Tidak ada migrasi database, tidak ada Edge Function baru/diubah, tidak ada langkah produksi Supabase untuk rilis ini (murni client-side).
