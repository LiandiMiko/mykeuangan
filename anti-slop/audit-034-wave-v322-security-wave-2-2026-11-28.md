## Temuan Forensik

- **T3/T4 (sesi & kata sandi)**: ganti kata sandi tidak meminta kata sandi lama dan tidak mencabut sesi di perangkat lain; hapus akun tanpa autentikasi ulang; `signOut` offline yang gagal membiarkan token lokal tetap ada sehingga aplikasi bisa masuk sendiri dengan token basi.
- **T6/T7/T8 (Telegram, desain lama)**: SATU bot bersama (`TELEGRAM_BOT_TOKEN` env, `supabase/functions/telegram-bot/core.ts:3`); OTP pairing disimpan PLAINTEXT di `telegram_pairings` (kolom `otp`, primary key) dan lookup webhook global `.eq('otp', otp)` tanpa filter user — siapa pun yang mendapatkan kode bisa mengklaim chat; policy `"own rows"` FOR ALL di `telegram_chats`/`telegram_pairings` membiarkan klien menulis baris chat/pairing sendiri; webhook memakai satu secret env bersama; `runRecurring`/pengingat selalu mengirim lewat bot bersama.
- **T9 (cron)**: `CRON_SECRET` tertulis plaintext di definisi job pg_cron (`supabase/schedule.sql`, placeholder `<CRON_SECRET_MIN_32_CHARS>`); tidak ada log pemanggilan job (kapan, oleh apa, berapa baris dibuat); `runRecurring` tanpa batas — satu jalan bisa membuat transaksi recurring tak terbatas untuk semua pengguna.
- **T11/T12 (XSS/CSP)**: `renderHtml()` (`web/ui-state.js:66`) hanya membuang `<script>`; 183 inline handler (`onclick` dll.) di `src/*.html` (133) + template `web/*.js` (50); CSP meta (`src/Index.html:8`) masih `unsafe-inline` + `unsafe-eval` dan `img-src https:` yang lebar.
- **T10/T13/S20 (idempotency & kunci)**: antrean offline tanpa idempotency key — retry setelah lost response bisa menduplikasi transaksi; kunci Gemini pengguna tersimpan plaintext di localStorage dan dipanggil langsung dari browser; anon key Supabase ter-commit di `web/config.js` (diterima sebagai permanen di riwayat git; keamanan bertumpu pada RLS yang terverifikasi — asumsi didokumentasikan, lihat butir 5 di bawah).

## Perubahan yang Diterapkan

1. **2.1 Sesi & kata sandi — T3, T4 (commit `ecdab22`, 9 file, +610/−53)**: ganti kata sandi wajib memverifikasi kata sandi lama (`signInWithPassword`) lalu mencabut semua sesi lain (`signOut({ scope: 'others' })`); hapus akun wajib autentikasi ulang — klien mengirim kata sandi saat ini, Edge Function `delete-account` memverifikasinya server-side sebelum menghapus; `signOut` offline yang gagal tetap membersihkan token lokal (`signOut({ scope: 'local' })` + sapu kunci `sb-*-auth-token`). Kunci Gemini dienkripsi saat disimpan dengan kunci PIN Wave 1 (AES-GCM, `v1:` + base64(IV‖ciphertext)); simpan ditolak bila DEK tidak ada (tidak pernah fallback ke plaintext); plaintext lama dimigrasi sekali; ada catatan risiko di modal pengaturan Gemini. Yang sengaja TIDAK dilakukan: pencabutan sesi target saat admin mereset kata sandi — `supabase-js 2.45.4` `admin.signOut` butuh JWT target, bukan userId, dan `admin-password` hanya memegang JWT admin; ada guard test yang menegaskan tidak ada pemanggilan `admin.signOut` di sana.
2. **2.2 Bot Telegram personal — bring your own bot (commit `29e4639`, 10 file, +1.215/−27)**: migrasi baru `supabase/migrations/20261128030000_wave2_personal_telegram_bots.sql` — tabel `telegram_bots` (`user_id` PK, `bot_username`, `bot_user_id`, `token_encrypted`, `token_iv`, `webhook_secret`, `link_secret`, `created_at`, `updated_at`; RLS aktif, `REVOKE ALL` untuk `authenticated`, tanpa policy — klien tidak pernah menyentuh tabel ini langsung; `ON DELETE CASCADE` ikut hapus saat akun dihapus). Token divalidasi lewat Telegram `getMe` (membuktikan token asli + mengambil username), dicek belum diklaim akun lain, lalu dienkripsi AES-GCM 256-bit dengan kunci server dari secret `TELEGRAM_TOKEN_ENCRYPTION_KEY` (SHA-256 dari secret sebagai kunci; IV acak 12 byte) dan tidak pernah dikirim kembali ke klien. Edge Function baru `telegram-setup` (verify_jwt true): `get_status`, `connect_bot`, `disconnect_bot`, `rotate_webhook`; `connect_bot` memasang webhook per pengguna (`?bot=<link_secret>` + `secret_token: webhook_secret`, `drop_pending_updates: true`) dan mengembalikan baris lama bila `setWebhook` gagal. Webhook `telegram-bot` me-resolve pengguna + token dari `link_secret`, memverifikasi header `secret_token` terhadap `webhook_secret` milik bot itu (T8; 404/403 generik tanpa rincian), lalu memakai token itu untuk SEMUA panggilan Telegram di request tersebut (`send()` me-resolve token per chat via `resolveBotTokenForChat`, cache 60 detik; `answerCallbackQuery` memakai `c.token`; unduhan foto/voice note di `ai.ts` memakai `c.token ?? OTP pairing kini disimpan sebagai hash SHA-256 (`otp_hash`, primary key; kolom `otp` plaintext dihapus; RPC `replace_telegram_pairing` meng-hash dengan pgcrypto) dan lookup webhook difilter `user_id` pemilik bot bila webhook personal (T7) — kode milik pengguna A tidak bisa menautkan chat lewat bot pengguna B. Tulis langsung `telegram_chats`/`telegram_pairings` dari klien dicabut (T6): `telegram_chats` kini SELECT-only baris sendiri, `telegram_pairings` tanpa akses klien sama sekali. Dedup `update_id` webhook kini per bot (PK komposit `bot_user_id, update_id`). `jobs.ts` (pengingat/notifikasi) otomatis mengirim lewat token bot pemilik tiap chat. `admin-user-ops` unlink dan `delete-account` ikut menghapus baris bot DAN memanggil `deleteWebhook` (best-effort); RPC `admin_unlink_user_telegram` ikut menghapus baris bot (tanpa `deleteWebhook` — webhook-nya tetap 404 setelah baris dihapus). ## Catatan Migrasi Pengguna

- **Urutan deploy setelah merge (WAJIB, oleh parent — produksi tidak disentuh di branch ini)**: (1) terapkan migrasi `20261128010000` (cron log), `20261128020000` (idempotency), `20261128030000` (bot personal) di SQL Editor — semuanya idempotent (`IF NOT EXISTS` / DO-block); (2) isi secret `TELEGRAM_TOKEN_ENCRYPTION_KEY` (string acak ≥ 32 karakter) + `CRON_SECRET` baru (sama dengan isi Vault `cron_secret`) di Edge Function secrets; (3) buat/update secret Vault `cron_secret` lalu jalankan ulang `supabase/schedule.sql`; (4) deploy ulang Edge Function `telegram-bot`, `telegram-setup` (verify_jwt true), `admin-user-ops`, `delete-account` (flip `delete-account` `verify_jwt` ke true saat deploy — tidak ada `config.toml` di repo; fungsi ini dulu di-deploy dengan `--no-verify-jwt`); (5) `supabase secrets set CRON_SECRET=<nilai sama>` + deploy ulang bila secret dirotasi.
- **Idempotency — urutan kritis**: migrasi `20261128020000` HARUS diterapkan SEBELUM klien baru ter-deploy — insert dengan kolom `idempotency_key` yang belum ada akan gagal di produksi.
- **Bot personal — transisi**: pengguna lama yang masih di bot bersama tetap berfungsi lewat fallback token env sampai mereka menghubungkan bot sendiri (menu "Bot Telegram Saya"). Liandi menghubungkan botnya sendiri lewat alur yang sama; setelah itu webhook botnya berpindah ke URL `?bot=<link_secret>` dan env `TELEGRAM_BOT_TOKEN` tinggal sebagai fallback. Di antara penerapan migrasi `20261128030000` dan deploy ulang `telegram-bot`, kode pairing OTP lama (max 10 menit) tidak berlaku — pengguna cukup membuat kode baru. Tanpa `TELEGRAM_TOKEN_ENCRYPTION_KEY`, `connect_bot` menolak dengan 500 dan bot lama tetap jalan.
- **Cron — rotasi**: lakukan rotasi `CRON_SECRET` mengikuti prosedur (a)–(e) di `supabase/README.md` (Vault + `supabase secrets set` + jadwal ulang job + cek `cron_job_runs`).
- **Admin fallback**: hitungan chat Telegram di statistik admin kini 0 bila RPC `get_admin_platform_stats` gagal — query langsung dari klien hanya mengembalikan chat milik admin sendiri (angka salah), jadi fallback-nya dihapus daripada menampilkan angka yang menyesatkan.
- **Cache token bot**: token bot di-cache 60 detik per pengguna di memori fungsi `telegram-bot`; setelah putus/hubung ulang bot, pesan bisa terkirim dari bot lama maksimal 60 detik (bot lama tetap milik pengguna yang sama).
- Update ke v3.20.6 menimpa v3.20.5 tanpa uninstall (keystore debug persisten yang sama, `versionCode 32006` > `32005`).
