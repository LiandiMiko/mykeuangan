## Temuan/Akar Masalah

- **Deno belum terinstal di VM** (`deno: command not found`). Diinstal lewat installer resmi (`curl -fsSL https://deno.land/install.sh | sh`) → Deno 2.9.8 (v8 15.0.245.2-rusty, TypeScript 6.0.3), di `~/.deno/bin/deno`.
- **`deno check` awal gagal 2 error tipe (TS2345)** — bukan bug logika, melainkan pengetatan Deno 2.9.8 / TS 6.0: `Uint8Array<ArrayBufferLike>` tidak lagi assignable ke `BufferSource` (yang kini menuntut `ArrayBufferView<ArrayBuffer>`). Lokasi: `sha256Bytes` (`crypto.subtle.digest`, baris 84) dan `verifyAssertionSignature` (`crypto.subtle.verify`, baris 236). Bukti ini masalah versi, bukan kode webauthn: `deno check` pada `admin-password/index.ts` (sudah live) gagal dengan 4 error kelas yang sama. Perbaikan: persempit tipe ke `Uint8Array<ArrayBuffer>` (tanda tangan fungsi + return `base64UrlDecode` + 3 deklarasi `let` di handler) — perubahan tipe saja, NOL perubahan runtime.
- **`deno check` polos gagal resolve `npm:@supabase/supabase-js@2.45.4`** ("Could not find a matching package ... in the node_modules directory") karena repo punya `package.json` + `node_modules`, sehingga Deno memakai mode node_modules manual. Perintah yang benar: `DENO_NO_PACKAGE_JSON=1 deno check supabase/functions/webauthn/index.ts` — Deno lalu mengunduh dari registry npm ke cache-nya. Import supabase-js di webauthn sengaja DINAMIS di dalam handler (bukan statis seperti fungsi lain) supaya helper murni tetap bisa diimpor langsung oleh `node --test` tanpa resolver `npm:` — didokumentasikan di header file.
- **Migrasi draf nyaris benar; satu celah nyata**: fungsi `purge_expired_webauthn_challenges()` adalah SECURITY DEFINER tetapi EXECUTE-nya jatuh ke PUBLIC secara default — siapa pun (anon) bisa memanggilnya. Isinya hanya menghapus challenge kedaluwarsa >1 jam (bukan data pengguna), jadi risikonya rendah, tetapi pola ini persis yang dilarang pelajaran Wave 4 (revoke dari PUBLIC saja tidak mencabut grant eksplisit `anon`). Diperbaiki: `REVOKE EXECUTE ... FROM public, anon, authenticated` + `GRANT EXECUTE TO service_role` (mengikuti pola migrasi `20261128120000`). Jebakan lain yang diperiksa dan TIDAK kena: migrasi tidak memanggil `hmac`/`digest` sama sekali (jadi kualifikasi `extensions.*` tidak relevan — `create extension if not exists pgcrypto` dipertahankan sebagai gaya repo, tidak dipakai kode); tidak ada `to_regproc` berargumen; `gen_random_uuid()` adalah `pg_catalog` (PG 13+), bukan pgcrypto.
- **Klien: `sb.functions.invoke` di supabase-js v2 MELEMPAR, bukan mengembalikan `{ error }`** — bukti langsung dari bundle ter-vendor `web/vendor/supabase.js`: `if (!_.ok) throw new s(_)` dengan `s = FunctionsHttpError` dan `.context` = Response mentah. Kode draf (`const { data, error } = await ...; if (error) throw error;`) tidak pernah sampai ke cabang error — lemparan FunctionsHttpError lolos mentah ke `formatBiometricFailureReason`, yang mengembalikan teks teknis Inggris ("Edge Function returned a non-2xx status code") ke pengguna. Diperbaiki: `callWebAuthnFunction` kini try/catch + membaca pesan ramah Indonesia dari body `{ error }` respons server lewat `extractWebAuthnServerError`, dengan fallback ramah (`FunctionsFetchError` → periksa koneksi; `FunctionsRelayError` → server bermasalah; default → verifikasi gagal, gunakan PIN). `formatBiometricFailureReason` juga dipetakan untuk ketiga nama error itu sebagai jaring pengaman.
- **Semantik kegagalan assertion server tidak dibedakan draf**: `finish-assertion` yang gagal (tanda tangan/counter/challenge ditolak) ditelan menjadi `null` — sama seperti server tidak terjangkau — sehingga percobaan gagal yang sah TIDAK dihitung pembatas percobaan biometrik (5 gagal → kunci 60 detik). Diperbaiki: `isWebAuthnServerRejection` membedakan pesan penolakan server (→ `false`, dihitung gagal) dari server tak terjangkau (→ `null`, PIN tetap bisa).
- **Kredensial bersifat per-RP-ID**: passkey yang didaftarkan di web (`liandimiko.github.io`) tidak bisa dipakai dari aplikasi Android (`https://localhost`) dan sebaliknya — pengguna mendaftar terpisah per platform. Ini sifat WebAuthn, bukan bug. Klien kini memakai `rpId` dari server bila ada (server-lah yang memverifikasi `rpIdHash`), jatuh kembali ke `resolveWebAuthnRpId()`.
- **Batasan yang disengaja (bukan bug)**: pernyataan attestation (`attStmt`) TIDAK diverifikasi rantai kepercayaannya — fmt apa pun diterima selama authData + clientData + rpIdHash + flag + kunci COSE-nya valid. Ini lazim untuk login passkey: attestation membuktikan asal-usul authenticator, bukan identitas pengguna; yang mengautentikasi adalah kunci + tanda tangan + challenge + counter. Didokumentasikan di header function.
- **Tiga tes lama mengunci status DRAF dan harus diperbarui** (bukan dihapus): guard di `tests/admin-last-activity-cleanup.test.js:158` dan `tests/wave4-low-hardening.test.js:109` ("migrasi WebAuthn tetap DRAF dan tidak diubah") + tes `tests/wave-v320-upgrades.test.js:199` (jalur web interim tanpa `__mkSb` — dengan flag menyala, `get()` tidak pernah terpanggil sebelum `begin`, sehingga `capturedGetOpts` null). Ketiganya diperbarui ke status terverifikasi / jalur server (lihat Perubahan).

Perlu Liandi di perangkat sungguhan — lihat checklist manual di change log (aktifkan biometrik, kunci aplikasi, buka dengan sidik jari, matikan biometrik, coba di web + Android).

- **Perilaku di aplikasi Android (Capacitor, origin `https://localhost`, rpId `localhost`)** — hanya dianalisis dari kode (rpId konsisten antara klien dan server), belum dicoba di APK sungguhan. WebAuthn di WebView Android + `localhost` sebagai rpId adalah jalur yang paling berisiko gagal dan wajib masuk checklist manual.
- **Fungsi purge belum berjalan otomatis** — belum ada cron yang memanggil `purge_expired_webauthn_challenges()`; tabel `webauthn_challenges` akan tumbuh sampai ada pemanggil (1 baris per percobaan; tidak memengaruhi login, hanya kebersihan).
