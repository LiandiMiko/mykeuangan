## Temuan / Akar Masalah (hasil pemetaan)

- **Tidak ada kolom versi di tabel mana pun.** `grep` seluruh `db/schema.sql` + `supabase/migrations/*.sql`: `version` tidak ada; `updated_at` hanya ada di `profiles` (migrasi 20261114000000) dan `telegram_bots` (Wave 2) — TIDAK di `transactions`, `wallets`, `budgets`, `financial_goals`, `assets`, `recurring`, `transfers`, `settings`, `categories`, `entities`. Jadi perbandingan `updated_at` tidak mungkin tanpa menambah kolom juga — dan `updated_at` kalah dari kolom versi: dua tulis dalam milidetik yang sama bisa berbagi stempel waktu yang sama (resolusi `timestamptz` + jam perangkat yang miring), sementara versi integer naik monoton dan tidak peduli jam.
- **Semua jalur update hari ini last-write-wins tanpa syarat.** `api_updateTransaction` (`supabase-records.js:123`): `.update(row).eq('id', id)` — tanpa syarat versi; bila 0 baris, yang dicek hanya "tidak ditemukan". Pola yang sama: `api_saveGoal` (update `.eq('id', goal.id)`), `api_saveRecurring` (update `.eq('id', d.id)`), `api_updateWallet` (update `.eq('id', id)`), `api_saveBudget` (upsert `onConflict: 'user_id,kategori,bulan'` — upsert tidak pernah bisa konflik, selalu menang), `api_deleteTransaction` / `api_deleteGoal` / `api_deleteBudget` / `api_deleteRecurring` (delete `.eq('id', id)` — hapus vs edit bersamaan tidak terbedakan dari "sudah tidak ada"). `api_deleteWallet` memanggil RPC `delete_wallet` (tanpa parameter versi).
- **Antrean offline memperbesar jendela balapan.** `web/ui-feat-offline.js`: `queueOfflineMutation` menyimpan `op` + `payload` + `targetId` + `createdAt` (+ kunci idempotensi T13) — TIDAK menyimpan versi record saat edit dibuat. `flushOfflineQueue` memanggil `_rawCallServer(op, ...args)` apa adanya; karena handler update tidak bersyarat, edit offline yang dibuat jam 08:00 lalu tersinkronisasi jam 12:00 akan menimpa perubahan perangkat lain jam 10:00 tanpa suara. Mekanisme pemblokiran per-target (§7b) hanya mengurutkan item dalam SATU flush, bukan mendeteksi perubahan server.
- **Cek sisi klien saja tidak cukup (syarat keras tugas).** Pre-check saldo transfer (`checkTransferBalancePrecondition`, `supabase-portfolio.js`) sudah mengakui pola ini sendiri di komentarnya: "hanya server yang menutupnya" (TOCTOU). Karena itu penegakan HARUS dievaluasi Postgres: `WHERE version = <yang diharapkan>` pada update/delete langsung (PostgREST), atau RPC yang mengunci baris (`SELECT ... FOR UPDATE`) lalu membandingkan versi di dalam transaksi.
- **Jalur tulis yang TIDAK butuh locking (tetap last-write-wins / atomik server, dicatat supaya tidak dikerjakan):** insert murni (`api_addTransaction`, `api_addTransfer` via RPC `transfer_between_wallets` — sudah idempotent + cek saldo server, `api_addWallet`, `api_addCategory`, `api_addAssetV2` tanpa dompet); operasi ADITIF atomik server (`api_contributeGoal`, `api_topUpAsset`, `api_withdrawAsset` — RPC membaca nilai kini lalu menerapkan delta, tidak memakai base dari klien); `api_refreshPrices` (update nilai aset oleh sistem); `api_saveDebtDueDates` / `api_savePayrollDay` / `api_savePrimaryBankWallet` / `api_savePeriod` (settings key/value tunggal, tidak ada identitas record untuk diversikan); `api_importTransactions` (insert massal baris BARU + dedup fingerprint — perilaku TIDAK diubah); `api_restoreBackup` (RPC restore eksplisit "ganti semuanya"); rename kategori/entitas (RPC atomik server; nama adalah natural key, tidak ada versi per record — rename bersamaan diserialisasi transaksi RPC, nama terakhir menang tetapi transaksi tetap konsisten); `api_deleteAsset` (tidak ada jalur edit aset biasa — hanya top-up/withdraw aditif — jadi tidak ada pasangan edit-vs-hapus); transfer (tidak ada jalur update transfer sama sekali — hanya tambah/hapus; hapus transfer yang sudah terhapus berperilaku seperti hapus transaksi: lihat rancangan hapus).
- **Klien belum pernah menerima versi dari server.** Semua select di `supabase-core.js` (`getInitialData`, `fetchBudgetsOnly`, `fetchWalletsOnly`, `fetchWalletsAndTransfers`, `fetchAssetsOnly`, `fetchRecurringOnly`, `goalFromRow`, `trxFromRow`) tidak memuat kolom versi, jadi dialog edit bahkan tidak tahu versi berapa yang sedang diedit.

## Rancangan (ditulis sebelum implementasi)

### Mekanisme yang dipilih: kolom `version` integer + trigger naik-otomatis

- **Kolom:** `version integer NOT NULL DEFAULT 1` di `transactions`, `financial_goals`, `budgets`, `recurring`, `wallets`, `assets` (migrasi baru `20261128110000_optimistic_locking.sql`, `ADD COLUMN IF NOT EXISTS` — idempotent; baris lama mendapat versi 1).
- **Trigger:** SATU fungsi `public.bump_version()` (`BEFORE UPDATE`, `NEW.version := OLD.version + 1; RETURN NEW;`) + satu trigger per tabel (`DROP TRIGGER IF EXISTS` + `CREATE TRIGGER`). Klien TIDAK PERNAH menulis kolom `version` sendiri — semua jalur tulis (PostgREST, RPC `contribute_to_goal`/`top_up_asset`/`liquidate_asset`/`rename_*`, refresh harga) otomatis menaikkan versi lewat trigger. Ini menutup celah "lupa menaikkan versi di satu jalur": perubahan apa pun dari sisi mana pun menaikkan versi.
- **Mengapa bukan `updated_at`:** butuh kolom + trigger yang sama juga (tidak ada di tabel user), tetapi stempel waktu bisa sama untuk dua tulis berurutan dan bergantung pada jam server yang benar; versi integer monoton, deterministis, dan perbandingannya (`=`) tidak punya ambiguitas pembulatan. `created_at` yang sudah ada di `transactions`/`financial_goals` tetap dipakai untuk urutan, bukan untuk konflik.

### Di mana penegakan (server, bukan klien)

1. **Update/delete langsung (PostgREST):** handler menambahkan `.eq('version', <versi-yang-diharapkan>)` pada `UPDATE`/`DELETE`. Postgres yang mengevaluasi syarat itu — klien kedua tidak bisa menimpa walau memanggil API yang sama. Bila 0 baris terpengaruh, handler membaca ulang baris itu: masih ada → KONFLIK (versi sudah bergerak); sudah tidak ada → untuk update berarti "dihapus perangkat lain", untuk delete berarti "sudah terhapus" (sukses idempotent, lihat bawah).
2. **Upsert anggaran (tidak bisa bersyarat lewat PostgREST):** RPC baru `public.save_budget_checked(p_kategori, p_bulan, p_jumlah, p_expected_version)` — `SELECT ... FOR UPDATE` (mengunci baris supaya dua RPC bersamaan diserialisasi; tanpa lock, cek-lalu-tulis di dalam RPC pun balapan), bandingkan versi, lalu insert-atau-update; mengembalikan `conflict=true` + baris kini bila versi tidak cocok. `SECURITY INVOKER`, `search_path = public`, `REVOKE ALL ... FROM public, anon` + `GRANT EXECUTE TO authenticated` (pola Gelombang 4 — revoke dari PUBLIC saja tidak menghapus grant eksplisit `anon`).
3. **Hapus dompet (RPC lama tidak berparameter versi — TIDAK diubah):** RPC BARU `public.delete_wallet_checked(p_wallet_id, p_expected_version)` — kunci baris `FOR UPDATE`, cocokkan versi, lalu mendelegasikan ke `delete_wallet(p_wallet_id)` yang lama. Nama fungsi berbeda supaya overload PostgREST tidak ambigu dan fungsi lama tetap utuh.
4. **Klien hanya mengirim ekspektasi + menampilkan dialog.** Cek di klien (`expectedVersion` dari state lokal) adalah optimasi UX (supaya dialog bisa menampilkan "apa yang berubah"), BUKAN penegakan — server tetap yang memutuskan.

### Dari mana `expectedVersion` berasal (kompatibilitas pemanggil lama)

- Handler menerima `expectedVersion` sebagai argumen terakhir (atau `'force'` — lihat bawah). **Bila tidak diberikan, handler mengambil dulu versi kini dari server lalu tetap memakai update bersyarat** (`fetch-then-conditional-update`). Ini tetap aman dari balapan karena syaratnya ada di `WHERE` — jeda antara baca dan tulis hanya membuat konflik lebih mungkin terdeteksi, tidak pernah membuat timpa diam-diam. Konsekuensinya: SEMUA pemanggil lama (form, laporan, backup/restore fallback, onboarding, rekomendasi AI) otomatis terlindungi tanpa perubahan — sesuai batas tugas. Satu SELECT tambahan per operasi tulis; operasi tulis adalah aksi pengguna (jarang), bukan polling.
- **Pengecualian PENTING — antrean offline:** `expectedVersion` di flush TIDAK BOLEH diambil saat flush (itu versi kini → selalu lolos → timpa diam-diam lagi). Versi HARUS ditangkap saat edit dibuat (enqueue) dan disimpan di item antrean (`baseVersion` + snapshot `base` berbentuk klien). Item antrean yang dibuat klien lama (tanpa `baseVersion`) memakai jalur fetch-first — perilakunya sama seperti hari ini (jendela migrasi satu versi, didokumentasikan jujur di bawah).

### Apa yang terjadi saat antrean offline berisi edit lama lalu sync setelah record berubah di server

1. Flush memanggil handler dengan `baseVersion` dari item. Update bersyarat gagal (0 baris) → handler melempar error konflik terstruktur (`code: 'MK_CONFLICT'`, `.conflict = { kind, id, operation, mine, current, base, deletedByOther }`).
2. Flush MENANGKAP konflik secara khusus — **bukan** `recordOfflineFailure`: konflik bukan kegagalan transient, jadi tidak menghabiskan `MAX_OFFLINE_RETRIES` (3x) dan tidak masuk daftar "Gagal". Item DIHAPUS dari antrean (sudah diputuskan nasibnya, jangan diulang), konflik DIPARKIR di `localStorage` (`mk_sync_conflicts_v1`, berisi `kind/id/op/args/base/mine/current`) dan flush LANJUT ke item lain (pemblokiran per-target §7b tetap berlaku untuk item yang sama targetnya).
3. Setelah flush selesai + `refreshFromServer` (state lokal kini = server), tampil SATU dialog ringkasan ("Ada N perubahan yang bentrok"), lalu dialog per konflik secara berurutan — bukan menumpuk dialog di tengah flush. Pilihan pengguna: **Pakai versi saya** (tulis ulang paksa: handler dipanggil dengan `'force'` — handler mengambil versi kini lalu update bersyarat terhadap versi itu; ini timpa yang DISETUJUI pengguna, bukan diam-diam), **Pakai versi terbaru** (buang edit saya, state lokal sudah = server), **Gabungkan** (hanya bila tidak ada field yang diubah KEDUA belah pihak — lihat bawah), atau **Nanti saja** (tetap terparkir; ditawarkan lagi saat flush berikutnya / saat aplikasi dibuka).
4. Bila record sudah DIHAPUS di server saat edit offline di-sync: konflik varian `deletedByOther` — pilihan: **Pulihkan sebagai data baru** (insert baru dari `mine`, id baru) atau **Biarkan terhapus**.

### Penghapusan vs edit bersamaan

| Skenario | Hasil |
|---|---|
| A edit, B hapus (edit masuk dulu) → hapus B | Hapus bersyarat `version = V_B` gagal (versi sudah naik oleh edit A) → B mendapat konflik "sudah diubah di perangkat lain": **Tetap hapus** (force) atau **Batal — simpan versi terbaru**. |
| A hapus, B edit (hapus masuk dulu) → edit B | Update bersyarat gagal + baris sudah tidak ada → konflik `deletedByOther`: **Pulihkan sebagai data baru** atau **Biarkan terhapus**. |
| A hapus, B hapus (keduanya) | Hapus kedua: baris sudah tidak ada → **sukses idempotent** (`alreadyDeleted: true`), bukan error. Pemanggil melewati toast Undo dalam kasus ini (undo atas hapusan perangkat lain tidak masuk akal). |
| A edit, B edit (keduanya) | Edit kedua gagal bersyarat → konflik edit-vs-edit dengan dialog 3 pilihan (lihat bawah). |
| Hapus offline diantrekan, lalu edit online masuk dulu | Sama seperti baris pertama — hapus di flush memakai `baseVersion` dari saat antre, jadi konflik terdeteksi di flush dan diparkir. |
| Edit offline diantrekan, lalu hapus online masuk dulu | Sama seperti baris kedua — diparkir sebagai `deletedByOther`. |
| Hapus offline diantrekan, lalu record dihapus juga di perangkat lain | Sukses idempotent saat flush; item antrean terhapus normal. |

### Dialog konflik (ramah awam, Bahasa Indonesia dulu)

- **Tidak pernah menampilkan error mentah.** Error `MK_CONFLICT` tidak sampai ke `showActionError`/`toUserErrorMessage` di jalur yang ditangani (form, laporan, flush); sebagai jaring pengaman, `toUserErrorMessage` memetakan `code === 'MK_CONFLICT'` ke kalimat umum ("Data ini baru saja diubah di perangkat lain. Muat ulang dan coba lagi.").
- Dialog (SweetAlert2, modul baru `web/sync-conflict.js`, diekspos lewat `window.__mkFeat.syncConflict`): judul "Ada perubahan yang bentrok", baris identitas record ("Belanja — Rp 50.000, 28 Nov 2026"), tabel field yang berubah (Kolom | Versi saya | Versi terbaru — hanya field yang nilainya berbeda, nominal diformat Rp, tanggal apa adanya, `active` → Ya/Tidak, `walletId` → nama dompet bila diketahui), lalu pilihan radio: **Pakai versi saya** / **Pakai versi terbaru** / **Gabungkan** (hanya bila tersedia) + tombol **Simpan Pilihan** / **Nanti Saja**.
- **Gabungkan (merge) — semantik yang dijanjikan:** per field, bandingkan `base` (saat saya mulai mengedit) vs `mine` vs `current` (server). Field yang hanya saya ubah → pakai saya; hanya server yang ubah → pakai server; tidak ada yang ubah → sama saja. Field yang diubah KEDUANYA (nilai akhir berbeda) → TIDAK bisa digabung otomatis → opsi Gabungkan DISEMBUNYIKAN dan dialog menjelaskan field mana yang bentrok. Tanpa `base` (pemanggil lama yang tidak menyertakannya), opsi Gabungkan juga disembunyikan — hanya Pakai versi saya / Pakai versi terbaru.
- **i18n:** semua string baru lewat `t('sync.*')` di `src/i18n.html`, ID + EN berpasangan (tes paritas `i18n-build.test.js` menjaganya). Bahasa dialog mengikuti `localStorage.lang` seperti dialog lain.
- **Bulk edit/hapus di laporan (`ui-pro-reports.js`):** konflik per baris TIDAK memunculkan dialog di tengah loop (akan menumpuk) — baris dihitung gagal, konfliknya diparkir, dan setelah bulk selesai dialog ringkasan konflik ditampilkan sekali.
